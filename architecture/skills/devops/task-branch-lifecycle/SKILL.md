# Task Branch Lifecycle

## When to Use
- Начинается любая задача, которая может изменить репозиторий.
- Агенты закончили изменения и запросили commit или push.

## When NOT to Use
- Пользователь задал только информационный вопрос без изменений репозитория.
- Пользователь принял завершённую задачу и требуется merge в `dev`: используй
  `devops/merge-accepted-task`.

## Start Gate
1. Выполни `git status --short --branch` и учти tracked, untracked и конфликтные
   файлы.
2. Если рабочее дерево не чистое, немедленно прекрати задачу.
3. Передай Architect список обнаруженных путей и причину блокировки.
4. Не выполняй `stash`, `clean`, `reset`, checkout файлов или автоматический
   commit. Вопрос решает пользователь через Architect.
5. Непушенные commits при чистом рабочем дереве не являются блокировкой.

## Branch Preparation
1. Определи текущую ветку.
2. Если она начинается с `neuro_`, продолжай работу в ней.
3. Иначе составь короткое смысловое имя задачи в `snake_case` и создай
   `neuro_<task_name>` от текущего состояния.
4. Не выполняй перед созданием ветки `fetch` или `pull`.
5. При коллизии используй числовой суффикс:
   `neuro_<task_name>_2`, `neuro_<task_name>_3`.
6. Передай Architect и остальным агентам имя рабочей ветки.

## Commit And Push
Запрос агентов должен содержать:

```text
summary:
files:
verification_context:
```

1. Проверь, что каждый переданный путь существует в изменениях Git.
2. Сопоставь объяснение с крупными зонами проекта: backend, frontend, обычные
   tests или architecture. Не выполняй детальный code review.
3. Не добавляй файлы, которых нет в явном списке handoff.
4. Запусти релевантные локальные проверки изменённых зон из project manifest
   или handoff владельца. Playwright не запускай.
5. Если обязательная проверка не прошла, не создавай commit и не выполняй
   deployment. Передай разработчикам команду, результат и затронутую зону.
6. Добавь в index только согласованные файлы и ещё раз проверь staged diff.
7. Создай commit с лаконичным сообщением на русском, отражающим смысл
   изменений.
8. Выполни push текущей ветки; при первом push задай upstream.

## Guardrails
- DevOps не исправляет код и тесты.
- Не включай посторонние изменения ради чистого `git status`.
- Не считай успешный commit достаточным подтверждением deployment.
- Не запускай Playwright как часть commit/deployment gate.

## Output

```text
branch:
commit_sha:
committed_files:
local_tests:
push:
blocked_handoff:
```
